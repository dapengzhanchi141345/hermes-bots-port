- **Never act on a subagent's backtest/gate verdict without a same-denominator re-check.** If it compared strategy-B's win-rate on a filtered SUBSET (e.g. events inside a liquidity pool) against strategy-A's win-rate on the FULL population, the gap is selection bias, not an edge — B only looks better because it skipped the bad events. **Rule:** re-score BOTH strategies on the identical full event set (B = A's action inside the gate + B's own action outside it), report Δ with a two-proportion z-test + a forward-horizon sensitivity, and only claim an edge if that shared-denominator Δ is significant and robust; otherwise keep the neutral default and mark "no claimed positive edge". A significant-looking p on the mismatched denominators (e.g. p=0.0015 on subset-vs-full) is the tell — re-run the fair test before scaling anything up or rolling anything back.

## 金策 bot 延迟/慢反应诊断 (Hermes 群聊 bot 链路)
用户抱怨"bot 反应慢"时按此序诊断, 别只盯着模型本身:
1. **DNS 挂起是最大单笔延迟来源**: 日志 `errors.log` 出现 `getaddrinfo failed` / `APIConnectionError` 时, 一次 API 调用可挂 50s+ (请求退避重试 2.1s+5.7s 累加), 即使缓存 97% 命中照样烧掉整段。对照本环境已知事实 (memory: github DNS 被掐, nameResolution 走 aliyun DoH `resolve-dns.bat`), agnes .cn/.com 端点同样会 DNS 抖动。治法: 域名解析走 aliyun DoH 兜底, 不裸信系统 resolver; 单次 000/超时重试 2-3 轮再下结论。
2. **单专属 key 免费档 RPM 顶格**: 专属 key (AGNES_KEY_CHIEF/RISK/RD) 各自独立, 但群聊并发 + cron 叠加 (30min 循环 / 08:30 简报 / 22:00 日报) 仍可能单 key 429。错峰: 多 cron 触发点错开 30-60s, 避免同 key 同窗口叠加。
3. **上下文膨胀是硬规律**: agent.log `API call` 行带 `in=` 与 `cache=X/Y (Z%)`。金策 bot 常态 65-90k tokens, 即使 97% 缓存命中, 解码仍 ~18s/轮。治法: 群聊场景把 `context_length` 从 512000 降到够用值 + 提前触发压缩 + 动态工具加载 (群聊高频 10-15 个工具, 其余 `tool_search` 按需拉), 每请求省 1000-3000 tokens。系统提示/skills 索引用两级分类索引替代全量列表 (社区实测 skills index 每轮烧 1500-3000 tokens)。
4. **bot 慢先扒日志不先猜**: 三金策 bot 的 `profiles/{chief,risk-officer,strategy-rd}/logs/agent.log` 的 `API call` 行带 `latency=`/`cache=`/`provider=`/`base_url`, 是延迟归因第一手证据 (provider 使用分布: `grep -oE 'provider=[a-z-]+' agent.log | sort | uniq -c`); `errors.log` 带 429/ConnectionError/DNS 明细。先定位慢在哪一层 (DNS 挂起 / 429 退避 / 基础 prefill / 工具多轮往返) 再动配置。
5. **provider 标签 ≠ 配置意图，但 key 归属要看命名 provider 块 (2026-09-28 两轮实测修正)**: agent.log `provider=custom` 只是对所有非内置端点的泛化标签 (绝大多数调用都标 `custom`), **不能凭标签断定实际走哪把 key, 也不能凭它断定"走了共享 key"**。真实 key 解析路径: 桌面端 `hermes_cli` backend 处理命名 provider (config `providers:` 块, 如 `agnes-bot-chief`) 时走 `hermes_cli/runtime_provider_custom.py` 的 `_resolve_named_custom_runtime`, 候选序 = 显式 api_key → provider 块 inline `api_key` → **`key_env` 读 profile `.env`** → host-gated env。专属 key (AGNES_KEY_*) 只要 config 里命名块写对 `key_env` 就能命中 (实测 risk 的 GRQZ 命中), 不必每请求都走命名路径。
   **验证配方 (实锤 key 归属的唯一可靠法):** 在 `hermes-agent/hermes_cli/runtime_provider_custom.py` 的 `_resolve_named_custom_runtime` 里 `api_key = next((c for c in candidates ...))` 之后**临时**加一行 `logger.info("key tail=%s base=%s prov=%s", api_key[-4:], base_url, requested_provider)`, 触发各 bot 一条群聊消息后读 `profiles/*/logs/agent.log` 对尾号 (专属 yBL7/GRQZ/HYTWey vs 共享 KNej/oPB3), 验证完**必须撤净** (grep 残留=0)。不打 key 明文、不留日志代码。用户问"是不是没走专属 key"时顺序不可倒: 先查各 profile `.env` 的 AGNES_KEY_* 尾号是否互异 + config 命名块 key_env 指向, 再上尾号日志实锤。
   **专属块加固 (2026-09-28 已做):** 三个命名 provider 块各加 `provider_key: <名>` 显式身份键, 防 custom 泛化路径降级到全局 key; 改动前照例备份 `profiles/*/backups/config.yaml.*`。
6. **群聊流式输出已开 (`streaming: true`), 勿重复配** — 首字延迟体感优化的大头在 1-4 的瓶颈层, 不在输出侧。
7. **config 改动的生效机制 (桌面端多 profile):** 各 profile 的 backend (`python -m hermes_cli.main --profile X serve`) 由 Hermes.exe 桌面端**懒启动 + 1h idle 自动收割**。改 profile config.yaml 后: 已存活的 backend 需 `taskkill /F /PID` 杀掉, 下一条群聊消息/定时任务到达时自动用最新代码+配置重启; 已被收割的 profile 本就下次触发即新起, 无需动。用 `powershell -Command "Get-CimInstance Win32_Process ... CommandLine"` 找带 `--profile chief` 的 python 进程 (MSYS bash 里 wmic 输出会因 GBK 报 \"Binary file matches\", 走 PowerShell 文件脚本更稳)。Hermes.exe 主进程 (Electron, 最小 PID) 别动。
8. **压缩阈值调紧只对会话起点有效:** 群聊场景可把 profile config `compression.threshold 0.5→0.25` + `target_ratio 0.2→0.1` (更早更狠压缩), 但**旧会话 (history 已几十轮) 仍带 70k 上下文跑** — 阈值改完要等新会话或手动 /clear 才见效, 别把\"改完立快\"当预期汇报。
- **6 节点研讨 cron 建好≠会发。** 到点触发后两个静默失败点: ①任务自身跑 LLM 时撞免费池 429 (errors.log 记 `RuntimeError: HTTP 429 您已达到免费用户的 API 速率限制`), 崩了**无自动重试**, 节点直接哑; ②bot-chat 投递 600s 超时 (cron log `bot-chat delivery ... timed out after 600s`) 内容没进群。用户报\"这个节点怎么没动静\"时**第一动作是 `cronjob list` 回读该任务 `last_run_at`/`last_status`/`last_error`** — `last_status=error` + `last_error` 带 429 就是撞限流没投出, 不是任务没建/没触发。治法: 多节点 cron **错峰 5-10min** 避开整点并发撞满免费池; 429 崩的节点**手动补发** (拉最新 daily_advisory+三线 brief 重算对账/开评, 不等下周期); 根治 = 错峰+降并发够用时才升级 Token Plan (让用户定, 不猜)。教训: **建完 cron 要回读验 last_status, 且每个到点节点主动 list 一次确认没 429 静默崩**, 别假设建了就发。
- **`deliver=bot-chat:<profile>` 在 profile backend 被 1h-idle 收割后首次 tick 可报 `Profile '<name>' does not exist` (2026-09-30 实测)**: 桌面端多 profile 架构下, 每个 profile 的 backend (`python -m hermes_cli.main --profile X serve`) 是**懒启动 + 1h idle 自动收割**。若某 profile 的 backend 已收割 (夜间 02:00 收口节点时 chief 空闲 >1h 很常见), cron tick 的 bot-chat 投递会先查 profile 注册表 → 找不到活跃 backend → 报 `does not exist`。**这不是配置 bug, 是 backend 冷启动时序问题**: 下一条到达 chief 的消息 (或下一个 cron tick) 会自动重新 spawn backend, 后续投递恢复。诊断: `grep "Profile.*does not exist" logs/gateway.log` 看时间戳, 对照 `taskkill`/idle-reap 日志确认收割时间; 若只在深夜 02:00 节点偶发且次日正常, 是冷启动时序, 不需要修。**不要给每个 profile 加 "常驻不收割" 开关** (会让 3 个金策 backend 永久占用内存), 只需接受深夜首 tick 可能丢失 + 次日 08:00 首 tick 兜底 (discussion_log 对账不依赖 02:00 单点, 08:00 开评会补读前日对账)。

## 盘节奏研讨 SOP (开评/对账成对 + DST 感知, 用户令 2026-09-28)
金策群每日研讨不是"每天一次", 而是**每个盘节点开/关成对**: 开评=发布三腿 (外汇/币/股指) 当日预期方向+关键位+应挂单清单 (预测基准); 关对账=读实际行情 vs 上一节点开评, 逐条判对/错/没吃到, 根因归类 (做反/漏吃/该持有未持有/事件压制)。节点时刻**按该盘当期时区规则现算, 不写死钟点** — 外汇 24h 连续跑, 冬夏令切换会让伦敦/纽约 kill zone 各移 1h, 固定钟点 cron 会撞错时段:
- 东京 09:00 JST = 北京 08:00 (全年固定); 关评 ~12:00 北京。
- 伦敦 08:00 当地: 夏 (BST, UTC+1, 3月最后周日↔10月最后周日) = 北京 15:00; 冬 = 北京 16:00。
- 纽约 09:30 当地: 夏 (EDT, UTC-4, 3月第2周日↔11月第1周日) = 北京 21:30; 冬 (EST) = 北京 22:30。美欧切换日错期窗口 (11月初~3月末) 两盘各按自己当期规则走, 脚本分别判。
- 悉尼 (可选节点) 10:00 当地, 澳 DST 规则反向 (10月第1周日↔4月第1周日): 夏北京 07:00 / 冬 08:00。
- 币圈 24h + 股指跟美盘节点; 切换日研讨里标一句"今日进入冬/夏令时, 该盘开评前后移 1h"。
**落地机制 (防走样):** 研讨节点落在 Hermes cronjob (每节点一条独立任务), 6 节点: 08:00/12:00/15:00(冬16:00)/18:00/21:00(冬22:00)/02:00。**投递通道必须 `deliver=bot-chat` 投本群「金策·宗师团」**, 不要 weixin (网关凭证常断, 22:00日报/08:30简报历史都撞过 blocked_config/Weixin token missing 而用户看不到消息) 也不要 `local` (本地存档投不到群)。建完 cron 必须 `cronjob list` 回读核对: 任务数、deliver、enabled、next_run_at 全对 — 本会话曾"列了 6 节点计划但只建了 1 条 cron", 到点静默不发, 用户报"怎么还没开始"才暴露; 计划≠调度, 建完即验。冬夏令切换日由总调度手动把 15:00/21:00 两条挪到 16:00/22:00, 群里标一句; 固定钟点 cron 配冬夏令切换日手动挪即可 (不必上 monitor 门, 切点就几天)。
**开评数据降级铁律 (本会话 21:30 卡 8min 的根因, 记死):** 研讨节点到点**无条件先用最新 `daily_advisory_*.json` + 三线 brief + `event_risk.json` 发开评** (30min 全循环保活), live MT5 实时价只做附注、20s 取不到就跳过, **绝不让实时价阻塞开评**。把"锦上添花的实时价"当成"开评前置"是主持人失职 — 顺序是"先基准表、后价格", 反过来就崩。mt5_launch/ate-python 的 live 步骤一律加 20s 超时自动降级到现有数据集, 不卡 shell 找 PATH。
**节点前 5 分钟落盘, 节点到点直投群:** 每节点开评前主持人先把基准表 (品种+现价/动量+挂单/空仓+打钩口径) 写 `data/discussion_log.jsonl` 并发群, 到点直接投, 取价事后补。
**对账是第一手进化资料, 必须落盘**: 每个节点一条追加 `data/discussion_log.jsonl` (时间+DST标记+三线预测+关评的命中/根因), 每月 P4 评审按"哪个时区规则下做的预测"分桶统计命中率; 落盘后研讨才算完成, 只在群里聊完即忘=白研讨。
**研讨闭环铁律 (空讨论不算数):** 每个开评节点必须出 1 条新做单思路 (品种+触发价+止损+RR+五验方案) 或上一验证批次 (rd_verify_batch) 的实数回评, 二者必居其一才收口; 对账节点把命中率+漏行情根因写 discussion_log 并进 rd_verify_batch。这是"讨论→可验证做单思路→五验→结果回群→再进化"的循环, 不闭环=白研讨。
