# MT5 Python Library Quirks (MetaTrader5 pip, build ~6182)

Pitfalls that recur on this host. All verified by probing the library, not guessed.

## 1. `positions_get(magic=)` / `orders_get(magic=)` filter does NOT work
The magic filter argument is silently ignored — `positions_get(magic=20260903)` still returns positions with magic 20260902. 
**Rule:** after every `*_get(magic=M)` call, manually filter `if p.magic == M`. Without this, cross-department modules (forex vs crypto magic) mis-adopt each other's positions and the loss state machine reviews the wrong trades.

## 2. Missing `ORDER_STATE_DONE` / `ORDER_STATE_EXECUTED` constants
This library version lacks `mt5.ORDER_STATE_DONE`, `mt5.ORDER_STATE_EXECUTED`, `ORDER_STATE_LOADED`. Present: PLACED, CANCELED, REJECTED, EXPIRED.
**Rule:** detect a pending-order fill WITHOUT state constants: the order disappears from `orders_get(ticket=t)` AND `history_orders_get(t).state` is NOT in {CANCELED, REJECTED, EXPIRED} → it filled. Never reference the missing constants (AttributeError kills the fill-check loop; fail-open hides it).
**Why it matters:** fill detection is the only path by which pending orders enter the position state machine; a crash here means fills silently stop being tracked and positions go naked.

## 3. Closed-spread / frozen-spread → retcode 10013 Invalid request
When a symbol's spread is absurd (e.g. 280 points vs normal 29), `order_send` for a close is rejected with 10013 no matter the deviation or filling mode (FOK/IOC both fail). Friday night / weekend FX halts are the usual cause; crypto is 24h so this is mostly an FX-symbols problem.
**Rule:** before closing, read `spread = (tick.ask - tick.bid) / info.trade_tick_size`. If ≥ 100 points, do NOT retry close loops — leave the position with its SL/TP attached (MT5 auto-manages it) and record "pending close, retry when spread normalizes" in the log/state. Never leave a position without SL/TP (naked) as a workaround; a position is acceptable only while its protective SL/TP is still armed.

## 4. Connection lifecycle is process-global; nested shutdown kills the parent loop
`mt5.initialize()` / `mt5.shutdown()` manage ONE shared terminal connection. If a helper function calls `mt5.initialize()+login()` at its top and `mt5.shutdown()` at its bottom, and the CALLER already holds the connection for its own loop, the helper's shutdown kills the caller's session — subsequent data fetches silently fail or return None and the whole cycle degrades.
**Rule:** establish ONE connection per run_cycle at the top; sub-functions (position management, fill checks) must NOT call initialize/shutdown themselves. Only the `__main__` self-check entry owns initialize/shutdown.

## 5. Login before symbols
`symbols_get()`/`symbol_info()` return unusable data before `mt5.login()` succeeds. **Rule:** order of operations: `initialize() → login() → symbol_info()/orders/positions`. Probe account (equity, leverage, positions) in the same logged-in block you plan to trade in.

## 6. `TradeOrder` has no `.volume` attribute
Attribute access raises AttributeError in this version. **Rule:** read order size from the state JSON written at placement (you always know the lots sent), not from the TradeOrder object. Print only `.ticket`, `.symbol`, `.type`, `.price`, `.sl`, `.tp`, `.expiration`, `.magic`, `.state` from the object. (Exception: when building a CANCEL request, the field IS available as `.volume_current` — see §12.)

## 7. Windows scheduled tasks: ONCE syntax
`schtasks /Create /SC ONCE /D <date>` fails (ONCE has no /D). **Rule:** one-shot → PowerShell `Register-ScheduledTask` with `New-ScheduledTaskTrigger -Once -Date 'YYYY-MM-DD' -AtStart 'HH:MM'` (note `-Argument`, NOT `-ArgumentList`, on `New-ScheduledTaskAction`). Recurring → `schtasks /SC MINUTE /MO 30` or `/SC MONTHLY /D 25 /ST 21:00` works fine.

## 8. Hermes cron delivery caveat
A locally-created Hermes cron job with `deliver=local` only fires when the Hermes gateway is running; it will not POST back into a CLI/desktop session. **Rule:** for 24/7 unattended trading loops, the heartbeat is a Windows scheduled task (zero LLM cost) running the one-shot cycle script; reserve Hermes cron/agent jobs for the human-facing daily digest at most. If you create a Hermes job, check `gateway_running` in the result and tell the user it is saved-but-inactive until the gateway starts.

## 9. GBK pipe + non-ASCII landmine — wider than emoji (2026-09-27 widening)
On this Windows host, `auto_run_cycle.py` captures each sub-process's stdout via `subprocess.run(..., text=True)`. That child's stdout is a **pipe, and Python picks the system code page (GBK/cp936)** for it — NOT the UTF-8 the source was read with. Any `print()`/`log.append()` of a character outside GBK raises `UnicodeEncodeError` **inside the child**; if that line sits near the top of the child's `run()`, the whole department fails and the caller's fail-open `try/except` swallows it into "(skip, using cache)".

**WIDENED rule (2026-09-27):** It is NOT just supplementary-plane emoji. These BMP non-ASCII symbols ALSO crash under the forced-GBK pipe: `⏸`(U+23F8), `⛔`(U+26D4), `✓`(U+2713), `✗`(U+2717), `⚠`(U+26A0), `→`(U+2192), `═══`(U+2550 box-drawing), `─`(U+2500), `—`(U+2014), `·`(U+00B7). The prior "most CJK is safe, only emoji is the landmine" reading was TOO NARROW — a whole batch of trading-module print lines using ⛔✓✗→═══ were silently failing-open every 30-min cycle for days (the 09-25 crash was a `📊`, the 09-27 recurrence was a `⏸`). **Rule: ban ALL non-ASCII in any print/log line that reaches the pipe. CJK 汉字 are in GBK and print fine; the dangerous set is symbols/punctuation/box-drawing/emoji outside GBK.**

**Batch audit+fix technique (reusable):**
```
# find the offenders (non-comment lines that reach stdout)
grep -nP '[⛔⏸✓✗⚠═→—·─⏰]|[\x{1F300}-\x{1F9FF}]' <file.py> | grep -vP '^\s*#'
# one sed sweep, verified by py_compile after:
sed -i 's/⛔/[stop]/g; s/⏸/[wait]/g; s/✓/[OK]/g; s/✗/[FAIL]/g; s/⚠/[!]/g; s/═/=/g; s/→/>/g; s/—/-/g; s/·/ ./g' <file.py>
python -c "import py_compile; py_compile.compile('<file.py>', doraise=True)"
```
Then re-run the module standalone (`python <module>.py`) to confirm RC=0 with no Traceback before re-running the full `auto_run_cycle.py` chain. Only file-WRITES via `open(..., encoding="utf-8")` may keep emoji — they never touch the pipe.

**Which modules are pipe-captured (audit these on any new tag):** `cio_orchestrator.py`, `crypto_pending.py`, `portfolio_governor.py`, `equity_pending.py`, `meta_evolver.py`, `daily_advisory.py`, plus the inline `subprocess.run([PY, "-c", ...])` scripts written inside `auto_run_cycle.py`. Modules NOT spawned as subprocesses (run in-process inside the orchestrator) are less fragile but still get their print routed through the cycle log, so keep them ASCII-tagged anyway.

## 15b. MT5 position/order objects are NOT dicts — no `.get()` (2026-09-27)
`mt5.positions_get()` returns `TradePosition` named-tuples, `mt5.orders_get()` returns `TradeOrder`. Both support **attribute access** (`.ticket`, `.tp`, `.sl`, `.entry_price`, `.volume`, `.type`, `.magic`, ...), but NOT **dict-style `.get()`**. Two recurring crashes in `crypto_pending.manage_positions` this session:
- `p.get("tp", 0)` on a `TradePosition` → `AttributeError: 'TradePosition' object has no attribute 'get'` — fix: `getattr(p, "tp", 0)`.
- Same object: read `.entry_price`, `.sl`, `.type` (0=BUY,1=SELL), `.volume` via attribute, NOT subscript.

**Rule:** anywhere you iterate `for p in mt5.positions_get(...)` or `for o in mt5.orders_get(...)`, treat the element as a **named tuple**, access fields by attribute, and use `getattr(p, "field", default)` for optional fields. If you built a dict earlier in the state-machine JSON (`st["filled"][tk]`), THAT one is a real dict and `.get()` is fine — the trap is only when the value comes straight from the MT5 C extension. Cross-ref §6/§10/§14 (other missing-field traps) — probe with `dir(p)` / `getattr` before assuming the field name.

## 15c. `risk = abs(entry - sl)` can be 0 → division blowup in L3/L4 exit protocol (2026-09-27)
In `crypto_pending.manage_positions`, the L3/L4 (break-even / chandelier) block computed `profit_r = (px - entry) / risk` with `risk = abs(f["entry"] - f["sl"])`. When a position's stored `sl` equals `entry` (a break-even already moved there, or a zero-width fill), `risk == 0` and the trend-branch line `profit_r = (px - entry) / risk if d > 0 else (entry - px) / risk` raised `ZeroDivisionError` and killed the whole crypto leg (exit code 1 every cycle). The range/intra branches already had `if risk > 0 else 0`; the **trend branch did not** — asymmetric guard. **Fix applied:** `profit_r = (px - entry) / risk if risk > 0 else 0`. **Rule:** any exit-protocol that divides by `risk` (or `d*(px-fill)/risk`) MUST guard `risk > 0` on EVERY branch (trend AND range AND intra); a zero/None SL in the stored state is a normal mid-management state, not an invariant. Related: the "near-zero-risk division blows up exp_R" backtest gotcha in the main SKILL.md — same root cause, different layer.

## 10. Non-standard field names in this build (6182)
`TradeOrder` has no `.volume`/`.price` (use `.volume_initial`, `.price_open`, `.time_expiration`); `SymbolInfo` has no `trade_volume_min`/`selected`/`trade_volume_step` (use `volume_min`/`volume_max`/`volume_step`, `select()` method); no `mt5.ORDER_TYPE_NAMES` dict (map type codes yourself: 0=BUY,1=SELL,2=SELL_LIMIT,3=BUY_LIMIT,4=SELL_STOP,5=BUY_STOP); `symbols_get_total` is actually `symbols_total`. Probe with `dir(obj)` before printing fields.

## 11. K-line request size ≠ data size; rebuild intraday anchors on D1
Requesting `copy_rates_from_pos(sym, H1, 0, 5)` returning 5 bars is NOT evidence "only 5 bars exist" — the demo feed has full 500-bar H1/D1 history for all 248 symbols. **Rule:** when a symbol's data looks thin, re-request with limit 500 before concluding. The real failure mode was a silent `except: return None` in `fetch_h1` swallowing a pandas tz-conversion error; the fix rebuilt `intraday_levels()` on D1 (previous-day high/low = most robust PDH/PDL source, ATR fallback 0.25×H4-ATR when H1<15 bars) instead of H1-UTC-day stitching.

## 12. Canceling pending orders: no `order_delete`; 10013 means the terminal is read-only, not bad params
This build has no `mt5.order_delete` — cancel via `order_send({'action': TRADE_ACTION_REMOVE, 'ticket': tk})`. When it returns `retcode=10013 'Invalid request'`, retry ONCE with the full-field cancel shape (§17: ticket + symbol + type + volume + price + sl + tp): a minimal REMOVE dict (ticket-only, or ticket+volume+type) can 10013 on its own while the same cancel succeeds with the full fields — observed both ways on the same order. If 10013 persists on BOTH shapes, the terminal is in a read-only state (Algo Trading button OFF, or the venue is closed). **Rule:** before concluding the cancel API is broken, probe write access with one tiny off-market pending order: `retcode=DONE` → writes work, retry the cancel; `10018 Market closed` → venue halted, wait; `10027` → Algo Trading off, ask the user to toggle it. Distinguish "terminal read-only" from "parameter shape" or you will burn time re-tuning a request that can't succeed until the button is on. When deduping stacked pendings, keep the NEWEST ticket and delete the older ones; only scrub state-machine `pending` entries for tickets that were ACTUALLY deleted, else reevaluate re-posts the ghosts.

## 13. Closing a position: don't guess the filling mode (retcode 10030)
Blindly trying `ORDER_FILLING_FOK` / `IOC` on a close can return `10030 'Unsupported filling mode'` — each symbol only accepts the filling modes its broker enables. **Rule:** read the `symbol_info(sym).filling_mode` BITMASK (bit 1=FOK, bit 2=IOC) and only send a supported mode; iterate candidate modes that the mask allows. Distinguish from 10013 (read-only terminal, §3/§12) — 10030 is a per-symbol parameter-shape problem, not a market/permissions problem.

## 14. Missing/renamed history & position-inspection APIs
Several convenient API names do not exist in this build: no `mt5.history_select`, no `mt5.positions_get_ticket`, no `mt5.history_deals_get()` with NO arguments (an unparameterized call returns 0 deals even when history exists), no `TradeDeal.position` (it is `position_id`), and `SymbolInfo.point` is singular (`points` → AttributeError). **Rule:** use `mt5.history_deals_get(start, end)` WITH explicit datetimes, `mt5.positions_get(ticket=tk)`, and `p.position_id` / `s.point`; when an inspection call surprises you, probe the real shape first with `dir(obj)` and `getattr(x, name)` before writing code — `TradeOrder.volume_current` (§6) is the same class of trap.

## 15. `order_send` returns a single `OrderSendResult` — read `.retcode`, never dict-subscript or 2-unpack
Probed 2026-09-27: `r = mt5.order_send(req)` returns **one** `OrderSendResult` object (named tuple, `len==11`), NOT a `(dict, code)` pair and NOT a dict. Three shapes crash on this host:
- `r['retcode']` → `TypeError: tuple indices must be integers`
- `res, code = ...` → `ValueError: too many values to unpack (expected 2)` (it has 11 fields)
- `res[0]` on REMOVE → `TypeError` (REMOVE path returns the object too; only `.retcode` is reliable)

**Correct:** `code = r.retcode` (also `.deal/.order/.comment/.request`). Success: `10009` request completed, `10008` order canceled (REMOVE ok), `10010` deal made (close ok).
**Retcode 10018 = 'Market closed':** removing a pending order on a halted symbol (FX over the weekend / frozen quote) returns 10018 and CANNOT succeed until the venue re-quotes — NOT a parameter bug, and it does NOT clear on immediate retry (quote stays frozen). **Rule:** in a ghost-pending scrub, treat 10018 as *skip-and-let-the-cycle-retry*: recheck next 30-min cycle / Monday open, where the auto cycle removes them automatically. Crypto (24h) clears instantly; only halted FX legs linger. Don't burn retries on 10018. Distinguish from 10013 (§3/§12 read-only terminal) and 10030 (§13 filling-mode) — 10018 is venue-halted, purely timing.

**Retcode 10015 = 'Invalid price' on a pending Limit/Stop: trigger price is too far from the live quote, NOT a filling-mode or read-only problem.** Sending `TRADE_ACTION_PENDING` for a SELL_LIMIT whose trigger sits too far above the market (a BUY_LIMIT too far below) returns 10015 and **the order is NOT placed** — but it looks identical to a parameter-shape error, so the instinct to flip the filling mode (FOK↔IOC↔RETURN) or re-probe the terminal is wrong; all three filling modes return 10015 on the same far trigger. **Rule:** on 10015 for a pending, fix the trigger price (bring it to a valid stop-limit distance of the live tick, matching the leg's ATR-based entry the engine's own `place_pending` computes) and re-send — do NOT keep cycling filling modes. To know the valid price window without guessing: read `symbol_info(sym)`'s `trade_stops_level` × `point` (min distance between a pending trigger and market) and the current `tick.bid`/`tick.ask`; a trigger must sit at least that far from the quote on the correct side. **Confirm success the same way as §15's 10009: a placed pending returns `retcode=10009` but the reliable ticket is read from a fresh `mt5.orders_get()` scan — the `OrderSendResult` for PENDING may carry the id on `.order`, but verify by re-reading `orders_get()`, not by trusting `res.order`.** Sync the placed ticket into the state-machine JSON (`pending_orders_state.json` `pending[tk]` + a `history` append) so the 30-min cycle adopts and manages it (fill/cancel/expiry); a pending that isn't in the state JSON is an orphan the cycle will never reconcile. **Never re-read a `TradeOrder` with `.price`/`.volume`/`.expiration` — those are the SymbolInfo names; on `TradeOrder` the fields are `.price_open`/`.volume_initial`/`.time_expiration` (§10). A `getattr(o,'price')` returning the wrong field or an AttributeError is a field-name miss, not a failed order — the 10009 already means it placed.**

## 18. PENDING 挂单的"附近价"几何 + 撤单副作用 (2026-09-30)
**SELL_LIMIT 只能挂在现价之上, BUY_LIMIT 只能挂在现价之下** — 挂反一侧 (SELL_LIMIT @ 低于 ask) 报 10015 Invalid price 且**不成交**。用户说"在 4195 附近挂空单"而现价 4195.5 时: 4195 的 SELL_LIMIT 无效 (比现价低), 合法挂位 = 现价上方最近的合规 tick (如 4198)。**Rule:** 挂 limit 单前先读 `tick.ask`, 确认挂单价在正确一侧且离开价 ≥ `trade_stops_level` 点距 (quirks §15 的 10015 诊断); "附近" = 向正确一侧取最近的合规价, 不是取整数字面值。**撤单副作用:** 撤掉一张失血点挂单不等于永久禁挂 — 下轮 30min 循环的 reevaluate 可能按同一 D1 信号原点位重挂 (同价 stack)。撤单同时要: ① 台账 `pending[tk]` 清票 + `history` 追加 (manual-cancel close loop, SKILL.md 已有); ② 若品种级负期望, 把该品种判进 D 级 (`is_symbol_allowed` 门控) 或写入 `dedupe_log` 同价去重, 否则 30min 后单又回来。**Rule:** 撤失血单 = 撤单 + 门控 双动作, 只撤单是半拉子工, 下轮循环就复现。

## 19. 平仓 P&L 算不死时别靠 history_deals, 用 entry/SL 直算 (2026-09-30)
`history_deals_get(start, end)` 在 demo 终端对刚触发的 SL 平仓常返回 0 笔 (历史同步延迟), 直接 sum deals 会把 P&L 记成 +0.00 污染台账。**Rule:** SL 触发的已知平仓直接按几何算: `pnl = -(entry - sl) × lots × contract_size` (SELL: entry>sl 止损 → 负), 与余额实差对账 (本例 SELL 0.01 @4185 → SL 4198 = -$13, 余额 987.03→974.03 恰好 -$13 吻合即验证通过); 台账写 P&L 必须过"余额实差核对"一道, 不能只信 deals 汇总。

## 20. 手动挂单也要写进 pending_orders_state.json 台账 (2026-09-30)
Hermes 侧手动 `order_send(TRADE_ACTION_PENDING)` 挂的单**不进 30min 循环的 pending 台账**, 循环既不知道它存在 (不接管 SL/TP/撤单/过期) 也不会对它做对账 — 孤儿单。**Rule:** 任何手动挂单, 挂完立刻: ① `pending_orders_state.json` 的 `pending[ticket_str]` 写全字段 (sym/side/ptype/entry/sl/tp/lots/regime/layer/risk_pct/placed_ts/expiry_ts/reason, magic 沿用 20260902-04 体系); ② `veto_log.json` 追加 PLACED 留痕 (gate=user_directed_rearm 或相应闸名); ③ 回读 `orders_get()` 确认 ticket 已存在再写台账 (先挂后记, 10009 才算挂成)。下轮 30min 循环按台账接管, 22:00 日报隔日对账才认得到这张单。
## 21. Dual-install hijack: worker/cron/relay binaries resolve to the AppData twin install (2026-09-30)
**Symptom cluster:** kanban workers repeatedly crash as `pid not alive / gave up after repeated spawn failures`; cron bot-chat delivery fails with `Profile 'chief' does not exist` even though `deliver=bot-chat` (bare value, correct); task state flips and claim_locks never clear. **Root cause (verify, don't guess):** this host has TWO Hermes installs — main `{{WORKBUDDY}}\国外模型\hermes` and twin `{{HERMES_HOME_PARENT}}\AppData\Local\hermes`. The desktop app's `sys.executable` lands in the twin's venv, and four resolution points call `shutil.which("hermes")` which hits the twin binary (PATH order puts the twin venv first): `hermes_cli/kanban_db_dispatch.py::_resolve_hermes_argv` (kanban worker spawn), `cron/scheduler_delivery.py` (bot-chat delivery), `gateway/run.py::_resolve_hermes_bin`, and `tools/bot_relay.py::_hermes_cli`. A worker spawned by the twin CLI sees the twin's kanban DB / profile tree, so it crashes or claims nothing; delivery says profile doesn't exist because it checks the twin's root.
**Fix (applied 2026-09-30, backups `*.bak-appdatafix` next to each file):** each of the 4 sites now falls back to its own install's module form (`sys.executable -m hermes_cli.main`) when the `which` result starts with the AppData twin prefix. **Procedure on any recurrence:** ① probe process trees: `Get-CimInstance Win32_Process` filtered on `CommandLine -like '*hermes*'` — map which gateway is parent, which `hermes.exe` the workers run, which venv each belongs to; ② diff the resolved CLI per install (venv `Scripts/hermes.exe` path differs — main vs AppData); ③ if a `which("hermes")`-style line still resolves to the twin, re-apply the module-form fallback at that site; ④ after ANY gateway restart, re-read `tasks` in the main kanban.db — killed gateways leave stale `claim_lock` rows pointing at dead PIDs; the new gateway sees them as claimed and never re-dispatches: `UPDATE tasks SET claim_lock=NULL, claim_expires=NULL WHERE status='ready' AND claim_lock IS NOT NULL;` ⑤ verify the fix by worker command line: a healthy worker shows `<main-install>\venv\Scripts\python.exe -m hermes_cli.main ...`, NEVER `{{HERMES_HOME_PARENT}}\AppData\Local\hermes\...hermes.EXE`. **Patching gotcha on this host:** bash heredocs mangle backslash literals in Python source (turns `"C:\USERS"` into an unterminated string) — when writing Windows path checks into these files, build the prefix at runtime with `chr(92)` joins (`'C:' + chr(92) + 'USERS' + chr(92) + '<USER>' + chr(92) + 'APPDATA'`), never raw backslash literals; then `py_compile` before restarting the gateway.

## 22. MT5 login constants live on the `ACCOUNT_ID`/`SERVER`/`PASSWORD` triple, not LOGIN/ACCOUNT (2026-09-30)
Modules under `multi_agent/trading/` (crypto_pending, pending_orders, equity_pending, trader_cio_gate) declare `ACCOUNT_ID` / `SERVER` / `PASSWORD` — there is NO `LOGIN`/`ACCOUNT` constant, so regex-grabbing `LOGIN|ACCOUNT` from source silently yields `login=0` and `mt5.initialize(login=0, ...)` fails with `(-2, 'Invalid params')`. **Rule:** import the module (`from multi_agent.trading import crypto_pending as cp`) and call `mt5.initialize()` bare + `mt5.login(cp.ACCOUNT_ID, password=cp.PASSWORD, server=cp.SERVER)`. Reusable check script shape: read positions via `p.price_open`/`p.volume`, orders via `o.price_open`/`o.volume_current` (§10), symbol scan for a ghost-order re-post via `orders_get()` filtered by symbol (e.g. D-grade vetoed symbols must show 0 orders + 0 recent deals), then `mt5.shutdown()` exactly once at the end (§4). **State-card staleness check:** node reports (开评/对账/日报) are snapshots — before acting on their 挂单/持仓 claims, re-read `positions_get()`/`orders_get()` once; reconcile any drift by appending a correction line to `data/discussion_log.jsonl`, never by mutating the original report.

## 17. Cancel (TRADE_ACTION_REMOVE) request dict: `comment` field rejected (2026-09-30)
`mt5.order_send({'action': mt5.TRADE_ACTION_REMOVE, 'order': tk, 'magic':..., 'symbol':..., 'type':..., 'volume':..., 'price':..., 'sl':..., 'tp':..., 'comment': '...'})` returns **None** with `mt5.last_error() == (-2, 'Invalid "comment" argument')` — the `comment` key is NOT accepted in the cancel request dict on this build. **Fix:** remove `comment` from the TRADE_ACTION_REMOVE dict; ticket + magic + symbol + type + volume_current + price + sl + tp are sufficient for a clean cancel. **Probe-and-confirm pattern:** always `mt5.orders_get()` first to confirm the ticket still exists, build the request from the live `TradeOrder` field values (not cached), call `order_send`, check `res is not None` before reading `res.retcode` (None + last_error(-2) = bad request shape, NOT a venue problem). PENDING/DEAL requests may accept `comment`, but cancel does not — do not assume symmetry across actions. Also verify the cancel actually landed: re-run `mt5.orders_get()` and confirm the ticket is gone; a None return with last_error(-2) means the order was NOT cancelled and is still live.
